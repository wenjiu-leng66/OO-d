主责：成员 1。对应脚本 [import_excel.py](../../database/seeds/import_excel.py)、编码表 [system_codes.csv](../../database/seeds/system_codes.csv) 与 [function_codes.csv](../../database/seeds/function_codes.csv)、核对 SQL [verify_import.sql](../../database/seeds/verify_import.sql) 和单元测试 [test_import_excel.py](../../tests/unit/test_import_excel.py)。表结构见 [数据字典](data-dictionary.md)。

## 1. 输入、输出和不提交的内容

| 输入 | 放在 | 用到的列 |
| --- | --- | --- |
| 部门信息表 .xlsx | `data/raw/` | 部门名称、部门经理、上级部门 |
| 应用软件功能权限清单 .xlsx | `data/raw/` | 软件系统、功能模块、功能点、功能说明，以及系统管理员、公司领导、部门经理、项目经理、普通员工 5 个角色列 |
| 员工信息表 .xlsx 或 UTF-8 .csv（可选） | `data/raw/` | 工号、姓名、公司、部门、岗位、性别、电话、邮箱，列名识别方式见第 5 节 |
| 系统短码表、功能点编号表 | `database/seeds/`，提交到仓库 | 见第 2 节 |

在仓库根目录执行：

```powershell
python database/seeds/import_excel.py --dept data/raw/市政公司部门信息表.xlsx --perm data/raw/市政公司应用软件功能权限清单.xlsx
```

脚本会提示输入两次初始密码。也可以用 `--initial-password` 直接给出，但密码会留在命令历史里，只建议在自动化环境中使用。拿到员工表后加 `--emp data/raw/市政公司员工信息表.xlsx`。

输出 `data/raw/seed_data.sql` 和核对报告 `data/raw/seed_data_report.txt`。它们含员工姓名、负责人姓名和密码哈希，`data/raw/` 被 Git 忽略，`scripts/check_repository.py` 也会拦截该目录下的文件。不要把输出改到别的目录后提交。初始密码本身不出现在任何输出里。

源表有脚本无法自动处理的问题时（下文标“停止导入”），脚本报出原表行号后退出，不会生成只导入一半的 SQL。能自动处理的问题写进核对报告。

## 2. 系统短码与功能点编号

权限码是 `系统码:功能点编号:动作`，如 `hr:f046:edit`（Q12），要求清单的行顺序变化时也不变，所以两段都来自仓库里的编码表，而不是导入时临时计算。

- `system_codes.csv`（code,name）：18 个系统的短码，2–16 位小写字母或数字，以字母开头。清单里出现表中没有的系统时停止导入，先在表里登记。
- `function_codes.csv`（code,system,module,function）：每个功能点的编号，按“系统 + 模块 + 功能点名称”对应。首次由当前清单生成，编号等于功能点在清单中的顺序，所以员工台账管理是 f046、用户管理是 f339。
- 清单里出现编号表中没有的功能点时停止导入。确认是新增的功能点后加 `--update-codes` 重新运行，脚本接着最大编号往后编并写回编号表，然后提交编号表，全组的编号才一致。
- 功能点、模块或系统改名时，直接改编号表里对应的名称，编号保持不变；否则会被当成“删除一个、新增一个”。
- 编号表里有、清单里没有的编号记为警告，编号保留，不分配给别的功能点。
- 功能点的库内 ID 就是编号，权限 ID = (编号 − 1) × 6 + 动作 ID，所以重复导入或调整行序后，ID 和权限码都不变。

## 3. 读表的通用规则

- 只读第一个工作表，在前 10 行内找表头，跳过全空行。
- 报告和错误里的行号都是 Excel 原表的行号，可以直接回原表定位。
- 单元格去掉首尾空白。
- 数值单元格转成文本：`12345678901.0`、`1.2345678901E10` 都转成 `12345678901`。工号和电话一律按文本处理。如果前导 0 已经被 Excel 当数字存掉，脚本无法恢复，源表应把这两列设成文本格式。

| 情况 | 处理 |
| --- | --- |
| 姓名为空 | 失败 |
| 有工号列，但该行工号为空 | 失败 |
| 工号是保留账号 admin 或 staff | 失败 |
| 工号与前面某行重复 | 失败；保留先出现的一行，报告写出两个行号 |

| 性别不是 男 / 女 / M / F | 照常导入，性别置空，记一条警告 |

## 6. 负责人按用户 ID 关联

最终存的是 `sys_dept.manager_user_id`，`manager_name` 只做核对。按姓名直接关联可能把管理权限给错人，所以规则如下：

1. 有员工表时，候选人先取“与负责人同名、且在该部门”的用户；没有的话，再取“同名、且在该部门直接下级部门”的用户。
2. 候选人恰好一人才关联。零人或多人时 `manager_user_id` 置空，报告记为 `[待核对]`，由管理员在系统里指定。只要部门对不上，即使全表只有一个同名的人也不关联。
3. 总公司根节点（Q-12，数据负责人核对）：原部门表中“总公司”和“公司领导”的负责人是同一个姓名，视为同一人。员工表里此人应在“公司领导”部门，按第 1 条的“直接下级部门”关联到总公司。
4. 没有员工表时（演示方案，Q24）：每个不同的负责人姓名生成一个用户，同名视为同一人；用户的部门取其负责的最后一个部门，直接关联到其负责的所有部门。

用课程员工表导入时，111 个部门的负责人全部按上述规则关联上：110 个部门的负责人在本部门找到唯一的同名用户，总公司的负责人在“公司领导”部门找到；重名没有造成歧义。

## 7. 角色初始化（Q-11，组内已定：Q16）

| 用户 | 初始角色 |
| --- | --- |
| admin | ADMIN 系统管理员，即超级管理员，只授予这一个账号（Q9） |
| 总公司或“公司领导”部门的负责人 | LEADER 公司领导 |
| “公司领导”部门的所有人（无论是否登记为负责人） | LEADER 公司领导（Q41） |
| 项目经理部的负责人 | PROJECT_MANAGER 项目经理 |
| 其他部门、分公司的负责人 | DEPT_MANAGER 部门经理 |
| 其他员工，包括副部长、项目副经理、副经理、副主任、经理助理等副职 | STAFF 普通员工；副职需要管理权限时由管理员另加角色（Q42） |

- 以上规则叠加：一人满足多条时取各角色的并集，所以允许多角色。
- 只有关联上用户 ID 的负责人才会得到管理角色。
- 不按“岗位”文字判断角色，因为岗位写法不统一；岗位只用于展示。
- 部门管理员 DEPT_ADMIN 是平台自己的内置角色（Q10），导入时只建角色、不分配给任何人，由超级管理员在系统里任命。管理范围是本部门及全部下级部门（与数据范围 DEPT 相同）；它的 `rbac:*` 授权待接口设计阶段确定。

| 情况 | 处理 |
| --- | --- |
| 软件系统、功能模块是合并单元格 | 合并单元格只有左上角有值，空白格沿用上一行的值（向下填充） |
| 功能点为空的行 | 跳过 |
| 第一个功能点之前没有系统或模块 | 停止导入 |
| 系统没有短码、功能点没有编号 | 停止导入，见第 2 节 |
| 同一模块内功能点重名 | 停止导入 |
| 不同系统下有同名模块 | 视为不同模块，如“供应商管理” |
| 一个格子写了多种动作 | 按 `/`、`、`、`,`、`，` 拆开，每种动作一条角色授权 |
| 无法识别的动作文字 | 停止导入，报出单元格位置 |
| 数据范围 | 按下面的“数据范围”表 |

数据范围（Q38）：

| 清单的角色列 | 查看、导出 | 新增、编辑、审批、删除 |
| --- | --- | --- |
| 系统管理员、公司领导 | ALL | ALL |
| 部门经理、项目经理 | ALL | DEPT（本部门及全部下级部门） |
| 普通员工 | 含“本人”的格子为 SELF，其余为 ALL | 同左 |

- 普通员工含“本人”的 6 个格子都在人力资源系统：员工台账管理、考勤管理、职业发展管理是“查看/编辑本人”，薪酬核算、福利管理、考核结果应用是“查看本人”，共拆出 9 条 SELF 授权。
- 受 DEPT 影响的是部门经理有非查看授权的 255 个功能点、项目经理的 88 个，共 351 条 DEPT 授权。
- 用户有多个角色时，同一权限码取最大范围 ALL > DEPT > SELF，由视图 `v_user_permission` 计算。

## 9. 核对方式

对应验收矩阵 T-12“导入与重复导入”。

1. **源记录与成功、失败**：每次导入都写核对报告，列出部门数、系统 / 模块 / 功能点数、权限数、角色授权数（含 DEPT、SELF 条数）、编号表新登记的数量、员工表源数据行数与成功、失败行数、负责人关联数和各角色人数，以及 `[失败]`、`[待核对]`、`[新编号]`、`[警告]` 的原表行号与原因。员工表的成功行数加失败行数等于源数据行数。
2. **入库后核对**：执行 SQL 后运行 `verify_import.sql`。各表行数应与报告一致；标注“返回空 = 正常”的查询必须为空（没有部门的用户、部门树断链或层级不符、功能点缺权限、权限码或权限 ID 与编号不一致、导入账号未设首次改密）；第 8 条把清单的一行从库里还原出来，与 Excel 对照抽查。
3. **重复导入**：生成的 SQL 先清空 10 张表，再按固定 ID 写入。同一份源表导入两次，`verify_import.sql` 第 9 条的业务数据指纹完全相同；只有密码哈希因随机盐而不同，所以指纹不含它。代价是系统里做过的修改（授权、改密码等）会被覆盖，因此只用于初始化和测试库，集成库导入前先备份。
4. **单元测试**：`python tests/unit/test_import_excel.py`，用合成数据覆盖本文的规则，不需要原始 Excel 和数据库。

## 10. 初始密码

导入账号的初始密码在运行时输入，不写进仓库，也不写进生成的 SQL 和报告（Q23）。所有导入账号的 `must_change_password` 为 1，首次登录必须先修改密码。哈希格式与 Spring Security 的 `Pbkdf2PasswordEncoder.defaultsForSpringSecurity_v5_8()` 相同，存成 `{pbkdf2@SpringSecurity_v5_8}` 加十六进制的盐和哈希；后端用 `PasswordEncoderFactories.createDelegatingPasswordEncoder()` 即可校验，最终算法与成员 4 统一。初始密码至少 6 位，演示时不要用电话号码。
