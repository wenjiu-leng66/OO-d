## 1. 输入、输出和不提交的内容

| 输入 | 放在 | 用到的列 |
| --- | --- | --- |
| 部门信息表 .xlsx | `data/raw/` | 部门名称、部门经理、上级部门 |
| 应用软件功能权限清单 .xlsx | `data/raw/` | 软件系统、功能模块、功能点、功能说明，以及系统管理员、公司领导、部门经理、项目经理、普通员工 5 个角色列 |
| 员工信息表 .xlsx 或 UTF-8 .csv（可选） | `data/raw/` | 工号、姓名、公司、部门、岗位、性别、电话、邮箱，列名识别方式见第 4 节 |

在仓库根目录执行：

```powershell
python database/seeds/import_excel.py --dept data/raw/市政公司部门信息表.xlsx --perm data/raw/市政公司应用软件功能权限清单.xlsx
```

拿到员工表后加 `--emp data/raw/市政公司员工信息表.xlsx`。

输出 `data/raw/seed_data.sql` 和核对报告 `data/raw/seed_data_report.txt`。它们含员工姓名、负责人姓名和密码哈希，`data/raw/` 被 Git 忽略，`scripts/check_repository.py` 也会拦截该目录下的文件。不要把输出改到别的目录后提交。

源表有脚本无法自动处理的问题时（下文标“停止导入”），脚本报出原表行号后退出，不会生成只导入一半的 SQL。能自动处理的问题写进核对报告。

## 2. 读表的通用规则

- 只读第一个工作表，在前 10 行内找表头，跳过全空行。
- 报告和错误里的行号都是 Excel 原表的行号，可以直接回原表定位。
- 单元格去掉首尾空白。
- 数值单元格转成文本：`12345678901.0`、`1.2345678901E10` 都转成 `12345678901`。工号和电话一律按文本处理。如果前导 0 已经被 Excel 当数字存掉，脚本无法恢复，源表应把这两列设成文本格式。

## 3. 部门信息表

| 情况 | 处理 |
| --- | --- |
| 部门名称为空的行 | 跳过 |
| 部门名称重复 | 停止导入 |
| 上级部门在表中不存在 | 停止导入 |
| 上级关系成环 | 停止导入 |

## 4. 员工信息表与组织映射

| 姓名 | 姓名、员工姓名、name |
| 公司 | 公司、分公司、所属公司、单位、所属单位、company |
| 部门 | 部门、所属部门、部门名称、department |
| 岗位 | 岗位、职位、职务、position |
| 性别、电话、邮箱 | 性别、电话 / 手机 / 手机号 / 手机号码 / 联系电话、邮箱 / 电子邮箱 / Email |

组织映射采用问题清单里的“数据规则候选”：

| 员工表的公司 | 员工表的部门 | 映射到部门表 | 例子 |
| --- | --- | --- | --- |
| 总公司（部门表的根节点名称） | 部门名称 | 部门名称本身 | 总公司 + 综合办公室 → 综合办公室 |
| 与部门相同 | 分公司名称 | 分公司节点 | 道路工程分公司 + 道路工程分公司 → 道路工程分公司 |
| 其他分公司 | 部门名称 | “分公司-部门” | 道路工程分公司 + 财务部 → 道路工程分公司-财务部 |
| 表中没有公司列 | 部门全称 | 原样使用 | 道路工程分公司-财务部 |

逐行检查。失败的行不导入，在报告里记为 `[失败]` 并给出原表行号：

| 情况 | 处理 |
| --- | --- |
| 姓名为空 | 失败 |
| 有工号列，但该行工号为空 | 失败 |
| 工号是保留账号 admin 或 staff | 失败 |
| 工号与前面某行重复 | 失败；保留先出现的一行，报告写出两个行号 |
| 映射后的部门不在部门表中 | 失败 |
| 整张表没有工号列 | 按顺序生成 E0001、E0002…，报告提示 |
| 性别不是 男 / 女 / M / F | 照常导入，性别置空，记一条警告 |
| 姓名相同、工号不同 | 照常导入，视为两个人 |

## 5. 负责人按用户 ID 关联

最终存的是 `sys_dept.manager_user_id`，`manager_name` 只做核对。按姓名直接关联可能把管理权限给错人，所以规则如下：

1. 有员工表时，候选人先取“与负责人同名、且在该部门”的用户；没有的话，再取“同名、且在该部门直接下级部门”的用户。
2. 候选人恰好一人才关联。零人或多人时 `manager_user_id` 置空，报告记为 `[待核对]`，由管理员在系统里指定。只要部门对不上，即使全表只有一个同名的人也不关联。
3. 总公司根节点（Q-12，成员 1 建议，待核对）：原部门表中“总公司”和“公司领导”的负责人是同一个姓名，视为同一人。员工表里此人应在“公司领导”部门，按第 1 条的“直接下级部门”关联到总公司。
4. 没有员工表时（演示方案）：每个不同的负责人姓名生成一个用户，同名视为同一人；用户的部门取其负责的最后一个部门，直接关联到其负责的所有部门。

## 6. 角色初始化（Q-11，成员 1 建议，待老师和组长确认）

| 用户 | 初始角色 |
| --- | --- |
| admin | ADMIN 系统管理员 |
| 总公司或“公司领导”部门的负责人 | LEADER 公司领导 |
| 项目经理部的负责人 | PROJECT_MANAGER 项目经理 |
| 其他部门、分公司的负责人 | DEPT_MANAGER 部门经理 |
| 其他员工 | STAFF 普通员工 |

- 一人负责多个部门时，取这些部门对应角色的并集，所以允许多角色。
- 只有关联上用户 ID 的负责人才会得到管理角色。
- 不按“岗位”文字判断角色，因为岗位写法不统一；岗位只用于展示。

## 7. 功能权限清单

| 情况 | 处理 |
| --- | --- |
| 软件系统、功能模块是合并单元格 | 合并单元格只有左上角有值，空白格沿用上一行的值（向下填充） |
| 功能点为空的行 | 跳过 |
| 第一个功能点之前没有系统或模块 | 停止导入 |
| 同一模块内功能点重名 | 停止导入 |
| 不同系统下有同名模块 | 视为不同模块，如“供应商管理” |
| 一个格子写了多种操作 | 按 `/`、`、`、`,`、`，` 拆开，每种操作一条角色授权 |
| 无法识别的操作文字 | 停止导入，报出单元格位置 |
| 不含“本人”的操作 | 数据范围为全部（ALL） |

## 8. 核对方式

对应验收矩阵 T-12“导入与重复导入”。

1. **源记录与成功、失败**：每次导入都写核对报告，列出部门数、系统 / 模块 / 功能点数、权限数、角色授权数（含 SELF 条数）、员工表源数据行数与成功、失败行数、负责人关联数和各角色人数，以及 `[失败]`、`[待核对]`、`[警告]` 的原表行号与原因。员工表的成功行数加失败行数等于源数据行数。
2. **入库后核对**：执行 SQL 后运行 `verify_import.sql`。各表行数应与报告一致；标注“返回空 = 正常”的查询必须为空（没有部门的用户、部门树断链或层级不符、功能点缺权限、权限码不一致）；第 7 条把清单的一行从库里还原出来，与 Excel 对照抽查。
3. **重复导入**：生成的 SQL 先清空 10 张表，再按固定 ID 写入。同一份源表导入两次，`verify_import.sql` 第 8 条的业务数据指纹完全相同；只有密码哈希因随机盐而不同，所以指纹不含它。代价是系统里做过的修改（授权、改密码等）会被覆盖，因此只用于初始化和测试库，集成库导入前先备份。
4. **单元测试**：`python tests/unit/test_import_excel.py`，用合成数据覆盖本文的规则，不需要原始 Excel 和数据库。

## 9. 初始密码

所有账号的初始密码都是 `123456`，只存哈希，上线前必须修改，演示账号不用电话号码作密码。哈希格式与 Spring Security 的 `Pbkdf2PasswordEncoder.defaultsForSpringSecurity_v5_8()` 相同，存成 `{pbkdf2@SpringSecurity_v5_8}` 加十六进制的盐和哈希。后端用 `PasswordEncoderFactories.createDelegatingPasswordEncoder()` 即可校验，最终算法待与成员 4 统一。
