= 一期数据库设计
:doctype: article
:toc: left


本设计依据实际迁移与JDBC实现编写，并随当前实现维护。

物理结构以link:../../database/migrations/V001__create_core_tables.sql[V001迁移]为准；逐字段说明见link:data-dictionary.md[数据字典]，清洗口径见link:import-rules.md[导入规则]。当前为10张表和1个核对视图，角色继承、约束和审计尚未建表。

== 1. 逻辑关系

[mermaid]
----
erDiagram
  sys_dept |o--o{ sys_dept : parent_id
  sys_dept |o--o{ sys_user : dept_id
  sys_user |o--o{ sys_dept : manager_user_id
  sys_user ||--o{ sys_user_role : user_id
  sys_role ||--o{ sys_user_role : role_id
  sys_role ||--o{ sys_role_permission : role_id
  sys_permission ||--o{ sys_role_permission : permission_id
  app_system ||--o{ app_module : system_id
  app_module ||--o{ app_function : module_id
  app_function ||--o{ sys_permission : function_id
  sys_action ||--o{ sys_permission : action_id
----

部门上级、用户所属部门和部门负责人都允许空值。一个用户可以被多部门引用为负责人，迁移未设置负责人唯一约束。用户/角色与授权使用稳定ID关联，不能用姓名消歧或数组行号替代标识。

[cols="1,1,1",options="header"]
|===
|对象 |设计职责 |关键约束
|sys_dept |组织邻接表、类型、层级与负责人 |名称唯一；parent/manager外键；五类型CHECK；无环和深度一致仍须导入验证
|sys_user |账号、摘要、组织、状态及role_version |工号唯一，非空电话唯一；启停与must_change_password分别CHECK；dept可空
|sys_role |角色码、启停、内置标志及permission_version |角色码唯一；状态/内置标志CHECK；保护规则在Service
|app_system/module/function |系统→模块→功能点目录 |系统码、功能码稳定；模块/功能名称在父级内唯一
|sys_action |固定六动作 |整数id为主键，动作code唯一；不能说主键就是动作文本
|sys_permission |功能点与动作组合的实际记录 |`(function_id,action_id)`和code唯一；导入/初始化派生
|sys_user_role |用户已分配角色 |`(user_id,role_id)`组合主键；关联可保留停用角色
|sys_role_permission |角色直接授权及逐码范围 |组合主键；data_scope仅ALL/DEPT/SELF
|===


== 2. 范围与有效权限

`data_scope`挂在角色—权限关系上，因此同一个角色可以对不同功能赋予不同范围。同码多角色取 `ALL > DEPT > SELF`，不同权限码不互相扩大。

`v_user_permission`实时汇总启用用户和启用角色的清单权限，便于核对；它没有处理首次改密、会话凭据、派生`rbac:*`和具体目标，不能单独作为完整鉴权入口。实际授权由link:../../backend-procedural/src/main/java/com/municipal/rbac/procedural/service/AuthorizationService.java[AuthorizationService]查Mapper并计算。二期引入继承时，不能只改视图而保持Java算法不变。

== 3. 完整性与删除

[cols="1,1,1",options="header"]
|===
|操作/关联 |数据库行为 |仍需服务层保证
|删除用户 |级联清sys_user_role，负责人外键SET NULL |目标范围、本人/admin保护
|删除角色 |用户角色及角色权限外键可级联 |内置保护、有用户确认、与授角协调、受影响用户版本递增
|删除有下级/员工的部门 |parent/dept外键默认RESTRICT |一期本就不开放组织增删改
|删除系统/模块/功能/权限 |多级外键含CASCADE，可能连带删除目录及授权 |不能声称外键自动阻止误删；运行期目录只读且导入受控
|删除仍被权限引用的动作 |默认RESTRICT |固定动作由迁移/初始化维护
|===


唯一约束为并发预检查兜底；外键并不表达角色授予权限、唯一ADMIN持有者、read前置或组织无环。当前物理删除没有历史审计或软删除恢复能力。

== 4. 两个版本、行锁和事务

* `sys_user.role_version`对应用户角色完整集合；`sys_role.permission_version`对应角色直接授权完整集合。CAS用旧值条件更新并递增，影响行数0返回409。
* 用户授角、角色授权替换及角色删除显式采用 `READ_COMMITTED`。其他事务由运行数据库配置决定，不能将MySQL默认隔离级别当作所有业务方法的实际级别。
* 用户授角先读取原集合，再按数字ID升序锁定原/新角色并集，检查角色及管理边界，最后用户CAS和关系替换；没有锁后重读原用户角色集合的额外步骤。
* 角色删除先锁角色、取得引用用户，再由Mapper递增用户版本和清理关系。固定顺序降低交叉锁冲突，但不宣称消除所有死锁。
* 多语句事务由Service边界提供；单独调用Mapper不自动具备完整业务原子性。H2测试不替代MySQL锁/方言与部署检查。

== 5. 索引与查询边界

用户工号/电话唯一索引用于账号定位及唯一性；用户部门、姓名、部门父级等有普通索引。关系表组合主键前缀支持按用户/角色查关联，反向关系有补充索引。

当前若干列表仍由 `findAll()`读入后在Java过滤/分页，姓名也可能在Java匹配。存在索引不表示这些列表已经使用数据库索引分页；也不能从视图定义推断1万员工下性能合格。优化须带真实查询、数据量、冷热条件、执行计划和端到端耗时，并保持范围过滤早于统计分页。

== 6. 初始化、导入与迁移

合成初始化必须显式启用且满足目标库前置条件，不覆盖已有用户/目录。真实原表通过离线脚本生成SQL；其中TRUNCATE清空十表数据再重载，并非增量迁移或可依赖普通事务回滚的操作。重复导入核对业务快照时排除随机盐摘要和时间字段，检查失败/未解析行及源表定位，不能只看程序退出码。

正式数量基准为111组织、18系统、115模块、359功能点、2154权限、10000员工加admin；清单五角色3549条授权，平台另补6条，完整条件下总计3555。合成样本不能替代原始资料的全量导入和性能证据。

V001/U001采用版本化文件命名，仓库没有因此自动启用Flyway迁移。首次空MySQL卷可由Compose挂载执行V001；已有卷不会自动重放。部署用命名卷保存数据，备份恢复另需演练；不能把卷持久化等同于备份。

应用使用独立数据库账号；实际权限需以部署授权为准，当前Compose本身不保证该账号只有CRUD。原始Excel、真实人员信息、口令/摘要及本地环境文件不进入公开仓库。当前也没有可依赖的授权成功审计记录，审计实现属于后续阶段。
