== 1. 引言

=== 1.1 编写目的

本文档说明一期 RBAC0 系统的详细设计：系统怎样分层、每个模块由哪些类负责、接口与数据怎样组织、关键流程怎样运行、并发与安全怎样保证、测试与部署怎样落地。

读者是课程教师、助教和项目组全体成员。教师可据此提问，组员可据此对照代码与测试。

=== 1.2 范围

本期只实现 RBAC0：用户、角色、权限及两类分配关系，权限取并集、默认拒绝，数据范围分 `ALL`、`DEPT`、`SELF` 三种。

角色继承（RBAC1）、静态/动态职责分离与基数约束（RBAC2）、激活角色切换、审计日志不在本期实现；界面中保留明确标注的静态占位页。

=== 1.3 术语

[cols="1,3",options="header"]
|===
|术语 |含义

|RBAC0
|基础角色访问控制：用户—角色—权限，不含继承和约束

|权限码
|`系统短码:功能点编号:动作`，例如 `hr:f046:edit`

|数据范围
|`ALL` 全部、`DEPT` 本部门及全部下级、`SELF` 仅本人

|整组替换
|提交完整集合覆盖原集合，而不是逐条增删

|版本号
|用户角色集合用 `role_version`，角色授权集合用 `permission_version`

|`rbac:*`
|由清单管理后台权限派生的平台管理权限码
|===

== 2. 总体设计

=== 2.1 系统架构

[source,mermaid]
----
flowchart LR
  B[浏览器] -->|HTTP 同源| N[Nginx]
  N -->|静态资源| V[Vue 3 界面原型]
  N -->|/api/v1 反向代理| S[Spring Boot 后端]
  S -->|Spring JDBC| D[(MySQL 8.4)]
  S -->|会话 Cookie| B
----

前端与后端同源部署：Nginx 同时提供静态页面和 `/api` 反向代理，浏览器只访问一个源，会话 Cookie 自动携带，生产环境不需要跨域。

=== 2.2 技术选型

[cols="2,3,2",options="header"]
|===
|层次 |技术 |选择理由

|前端
|Vue 3、Element Plus、Vue Router、Vite
|组件化、路由守卫成熟；与成员 2、3 的现有代码一致

|后端
|JDK 21、Spring Boot 3.3.5、Spring JDBC
|依赖注入、事务、Web 基础设施完整；SQL 可控，便于审计和优化

|数据库
|MySQL 8.4 LTS、InnoDB、utf8mb4
|支持 CHECK 约束、递归 CTE；中文与事务可靠

|部署

=== 2.3 分层与模块划分

[cols="2,3,2",options="header"]
|===
|层 |职责 |主要类

|边界层
|接收 HTTP、绑定并校验 DTO、返回视图
|8 个 Controller

|控制层
|用例编排、业务规则、事务边界、鉴权调用
|10 个 Service

|仓储层
|参数化 SQL，屏蔽数据库
|4 个 Mapper

|数据载体
|数据库行、入站 DTO、出站视图
|PO、Requests、Views、ErrorVO

|横切
|统一异常、安全与会话
|ApiException、GlobalExceptionHandler、SecurityConfig、BrowserSecurityConfig
|===

依赖规则：

* Controller 不得直接依赖 Mapper，全部经过 Service。
* Service 不得把 PO 直接返回给 Controller，必须转 `Views`。
* Mapper 不得调用 Service，单向依赖。
* 权限判断只在 `AuthorizationService`。
* `@Transactional` 只在 Service 层。

=== 2.4 设计方法

* *用例驱动*：先由用例图确定参与者与系统边界，再由领域模型抽取概念，最后由序列图验证关键流程。
* *边界—控制—实体（BCE）*：Controller 是边界类，Service 是控制类，PO/领域概念是实体类，Mapper 是仓储类。
* *GRASP 职责分配*：权限计算交给信息专家 `AuthorizationService`；Controller 作为控制器；Mapper 作为间接层；接口与实现保持低耦合、高内聚。
* *契约先行*：OpenAPI 是前后端共同依据，字段、错误码、权限码在契约中固定，代码与测试向契约对齐。
* *默认拒绝*：没有明确授予的权限一律拒绝，前端隐藏按钮只是展示，不作为安全边界。

== 4. 数据库设计

=== 4.1 设计原则

* 全组只有一套表结构，以 Flyway 命名的迁移文件发布，两套后端共用。
* 表名前缀：`sys_` 为系统表，`app_` 为资源目录；视图前缀 `v_`。
* 索引前缀：`uk_` 唯一、`idx_` 普通、`fk_` 外键、`ck_` 检查。
* 字符集 `utf8mb4`；存储引擎 InnoDB；MySQL 8.0.16 以上使 CHECK 生效。
* 原始 Excel 不进入仓库；导入走离线脚本。

=== 4.6 有效权限视图

`v_user_permission` 汇总每个启用用户通过启用角色获得的权限：

* 只统计 `sys_user.status = 1` 且 `sys_role.status = 1` 的角色。
* 同一权限码被多个角色授予时，按 `ALL > DEPT > SELF` 取最大范围。
* 查不到即无权限，对应默认拒绝。
* 阶段二加入角色继承时，只改视图为递归 CTE，调用方不变。

== 5. 接口设计

=== 5.1 通用约定

* 路径前缀 `/api/v1`，请求与响应均为 JSON。
* 成功直接返回对象或数组；分页为 `{items, page, pageSize, total}`，页码从 1 开始，默认 20，最大 100。
* 删除成功返回 204，无响应体。
* ID 一律为字符串；用户状态 `ENABLED` / `DISABLED`；角色状态为布尔 `enabled`。
* 失败统一包络：`{error: {code, message, requestId, details}}`。

=== 5.2 会话与 Cookie

* 服务端 `HttpSession`，Cookie 名 `JSESSIONID`，`HttpOnly`、`SameSite=Lax`；HTTPS 部署启用 `Secure`。
* 登录成功轮换会话 ID，防会话固定。
* 退出使旧会话失效。
* 每个请求重新读取账号、角色与授权，不把权限缓存在会话里。

=== 5.5 整组替换与版本

* `PUT /users/{id}/roles`：请求 `{roleIds, version}`，空数组表示撤销全部角色。
* `PUT /roles/{id}/permissions`：请求 `{grants: [{code, scope}], version}`，空数组表示撤销全部授权。
* 版本来自对应 GET；提交旧版本返回 409 `VERSION_CONFLICT`，`details.currentVersion` 告知当前值。
* 同一请求内拒绝重复 ID / 重复权限码；未知码、非法范围返回 400。
* 非查看动作必须同时包含该功能点的查看权限，否则 400 `READ_REQUIRED`。
* 成功在同一事务内整组替换并递增版本；任一步失败全部回滚。

=== 5.6 权限码与 `rbac:*` 映射

清单权限格式为 `系统短码:fNNN:动作`，动作固定为 `read/create/edit/approve/export/delete`。显示名称可以改，权限码不能改。

|===
|清单权限 |派生管理权限

|`sys:f339:read`
|`rbac:user:read`

|`sys:f339:create`
|`rbac:user:create`

|`sys:f339:edit`
|`rbac:user:update`、`rbac:user:assign-role`

|`sys:f339:delete`
|`rbac:user:delete`

|`sys:f340:*`
|`rbac:role:*`

|`sys:f341:read`
|`rbac:permission:read`

|`sys:f341:edit`
|`rbac:role:grant`

|`sys:f342:read`

|===

派生码不能直接写入角色授权，范围继承源清单授权。

== 6. 后端模块详细设计

=== 6.1 认证与会话

*职责*：工号/手机号登录、退出、修改本人密码、首次改密限制。

*关键类*：`AuthController`、`AuthService`、`MeController`、`MeService`、`AuthorizationService`、`UserMapper`。

*输入输出*：

* 登录：`{username 或 phone, password}`，返回安全视图与 `JSESSIONID`。
* 改密：旧密码、新密码；新密码 8–128 字符，且不能与旧密码相同。
* 本人信息：不含密码哈希；有效权限带来源角色。

*主流程*：

. 按工号或手机号查用户。
. 校验密码哈希；失败统一 401，不区分账号不存在、密码错、停用、锁定。
. 成功轮换会话 ID，记录用户 ID 与凭证版本。
. 若 `must_change_password = 1`，只放行本人信息、改密、退出。
. 改密成功后清除标记，凭证版本加一，使其他旧会话失效。

*事务*：改密在单条更新中完成；登录不写业务表，仅更新最后登录时间（可选）。

*失败分支*：401 统一登录失败；400 旧密码错误或新密码不合法；403 未改密时访问其他接口。

*需求*：LOGIN-01 至 LOGIN-05。

=== 6.2 授权

*职责*：所有受保护请求的认证、权限码、数据范围、目标对象检查。

*关键类*：`AuthorizationService`，协作者 `UserMapper`、`RoleMapper`、`DepartmentMapper`。

*核心方法*：

[cols="2,3",options="header"]
|===
|方法 |作用

|`current(session)`
|取当前登录用户，校验会话与凭证版本

|`requireUserId(session)`
|只取用户 ID，未登录 401

|`ready(session)`
|会话有效且已完成首次改密

|`effectivePermissions(userId)`
|计算角色权限并集与范围

|`require(session, code)`
|要求权限码，否则 403

|`target(session, code, id)`
|要求权限且目标在范围内

|`visible(actor, scope)`
|返回范围谓词，用于先裁剪再分页

|`covers / coversDepartment`
|判断目标或部门是否在范围内

|`widerScope(a, b)`
|`ALL > DEPT > SELF` 合并
|===

*算法*：

[source,text]
----
effectivePermissions(userId):
  roles = 已分配且启用的角色
  codes = 空集
  scopes = 空映射
  for role in roles:
    for grant in role.directGrants:
      codes.add(grant.code)
      scopes[grant.code] = widerScope(scopes[grant.code], grant.scope)
  return codes, scopes

authorize(session, code, targetId):
  actor = current(session)                 # 401
  if code not in effectivePermissions(actor).codes: return 403
  scope = scopes[code]
  if scope == SELF and targetId != actor.id: return 403 OUT_OF_SCOPE
  if scope == DEPT and targetDept not in subtree(actor.deptId): return 403 OUT_OF_SCOPE
  return ALLOWED
----

*关键约束*：

* 身份只从服务端会话取，忽略请求里的用户、角色、权限字段。
* 不存在与范围外统一 403 `OUT_OF_SCOPE`，`details` 为空。
* 列表先裁剪范围，再筛选、计数、分页。
* 查看范围不放大编辑范围，不同权限码分别计算。

*需求*：AUTHZ-01 至 AUTHZ-03、GRANT-04、GRANT-05。

=== 6.3 用户管理

*职责*：范围内用户查询、新增、编辑、启停、重置密码、删除、角色整组替换、账号保护。

*关键类*：`UserController`、`UserService`、`UserMapper`、`RoleMapper`、`AuthorizationService`。

*主流程*：

. 认证并检查 `rbac:user:*` 权限与目标范围。
. 查询先按 `ALL/DEPT/SELF` 裁剪，再按部门、工号、姓名、角色筛选并分页。
. 新增校验工号唯一、手机号可空但非空唯一；初始密码来自部署配置。
. 编辑不允许把用户调到范围外部门。
. 删除清理用户角色关联，并把负责部门的 `manager_user_id` 置空。
. 角色替换见 6.4 与第 8 章。

*保护规则*：不能停用、删除自己，不能修改自己的角色；唯一 `admin` 不能被停用、删除或改角色，违反返回 409 `PROTECTED_ACCOUNT`。

*事务*：新增、编辑、删除、角色替换均在 Service 事务内。

*需求*：USER-01 至 USER-07、GRANT-01、GRANT-03。

=== 6.4 角色与授权

*职责*：角色增删改查、启停、内置角色保护、删除确认、角色成员查询、角色授权整组替换。

*关键类*：`RoleController`、`RoleService`、`RoleMapper`、`UserMapper`、`AuthorizationService`。

*主流程*：

. 认证并检查 `rbac:role:*` 或 `rbac:role:grant`。
. 新增/编辑校验角色编码唯一。
. 停用角色后，该角色不再贡献权限，下一次请求即生效。
. 删除先锁定角色行，再检查内置角色、`ADMIN`、是否仍有用户。
. 有用户且未确认返回 409 `ROLE_HAS_USERS`；确认后清理关联并递增受影响用户的角色版本。
. 授权替换校验权限码合法性、重复码、`READ_REQUIRED`，在同一事务内整组替换并递增 `permission_version`。

*事务与并发*：见第 9 章。

*需求*：ROLE-01 至 ROLE-04、GRANT-02。

=== 6.5 组织架构

*职责*：只读部门树、负责人、员工数、部门及全部下级成员。

*关键类*：`DepartmentController`、`DepartmentService`、`DepartmentMapper`、`AuthorizationService`。

*主流程*：

. 读取全部部门，在 Java 中按 `parent_id` 组装树；111 个节点，内存计算足够。
. 部门成员先按调用者范围裁剪，再返回。
. `SELF` 范围只返回本人，不能借部门列表看到同事。
. `DEPT` 范围包含本部门及全部下级。

*需求*：DEPT-01、DEPT-02、AUTHZ-03。

=== 6.6 资源目录

*职责*：系统、模块、功能点、权限的只读查询、筛选、分页与统计。

*关键类*：`CatalogController`、`CatalogService`、`CatalogMapper`。

*主流程*：

. 按系统、模块、关键词筛选，分页返回。
. 返回全局统计：18 系统、115 模块、359 功能点、2154 权限。
. 目录只读，由导入维护，不提供网页增删改。

*需求*：CAT-01 至 CAT-03。

=== 6.7 门户与员工台账

*职责*：按查看权限生成菜单、功能点六动作状态、我的权限、员工台账查询与编辑。

*关键类*：`PortalController`、`PortalService`、`LedgerService`、`MeController`、`MeService`。

*主流程*：

. 菜单只展示有 `read` 权限的系统、模块、功能点。
. 功能点页按有效权限返回 6 个动作的可用状态与数据范围。
. 台账列表按 `hr:f046:read` 范围裁剪；编辑只允许电话、邮箱，按 `hr:f046:edit` 范围检查。
. 查看范围与编辑范围分别计算，不能因为查看 `ALL` 就允许编辑 `ALL`。

*失败分支*：范围外 403 `OUT_OF_SCOPE`；提交电话/邮箱以外字段 400 `FIELD_NOT_EDITABLE`。

*需求*：PORTAL-01 至 PORTAL-06。

=== 6.8 横切与错误处理

* `ApiException` 携带 HTTP 状态、错误码与 `details`。
* `GlobalExceptionHandler` 把业务异常、参数校验、JSON 解析错误统一为错误包络；未知异常记日志并返回 500，不输出堆栈。
* `SecurityConfig` 配置会话与安全策略；`BrowserSecurityConfig` 配置开发期 CORS。
* 响应只通过 `Views` 构造，绝不直接序列化 PO，避免密码哈希泄漏。

=== 7.2 路由守卫与权限元数据

* 路由 `meta.permission` 或 `meta.permissionOf` 声明所需权限码。
* 未登录跳转 `/login`，并带上原始地址。
* 已登录但无权限跳转 `/403`。
* 多个必需查看权限采用 AND，必须全部具备才能进入。
* 菜单隐藏、直接输入 URL、按钮状态共用同一判断核心，避免“菜单隐藏但直接访问成功”。

=== 7.3 菜单与按钮

* 登录后调用 `/me/permissions` 获取有效权限与来源角色。
* 菜单只显示有查看权限的功能点。
* 按钮按对应动作权限启用或置灰；置灰只是展示，后端仍会拒绝越权请求。
* 权限未加载完成时默认拒绝，不先显示可操作按钮。

=== 7.4 API 客户端与模拟后端

* 统一 HTTP 客户端，按配置切换模拟后端与真实后端。
* 开发期 Vite 代理 `/api`；生产由 Nginx 同源代理。
* 401 清会话并跳登录；403 显示无权页；409 提示重新读取后复核，不自动重试覆盖。
* 原型使用内存模拟数据，刷新恢复；演示账号与密码只用于原型，不连接真实数据库。

=== 7.5 关键页面交互

*用户管理*：按部门、工号、姓名、角色筛选；分页；行内启停、重置、删除；分配角色时读取当前集合与版本，提交完整集合。

*角色管理*：列表、新增、编辑、启停、删除；删除有用户时二次确认。

*角色授权*：资源目录按系统、模块、功能点展开；每条授权带数据范围；勾选非查看动作时自动勾选查看；翻页不丢勾选；保存整组替换。

*员工台账*：按范围展示；只允许编辑电话、邮箱；范围外请求被拒绝且不返回对象字段。

=== 7.6 页面状态与并发

[cols="2,3,3",options="header"]
|===
|状态 |页面行为 |禁止

|加载中
|显示加载状态，保存暂不可用
|权限未回来就先允许操作

|空结果
|显示空状态，允许合法空集合
|把空数组当故障

|401
|清会话，跳登录
|保留上个账号的菜单

|403
|显示无权，停止编辑
|改 URL 或隐藏错误继续保存

|409
|提示版本冲突，重新读取后复核
|自动重试覆盖他人修改

|5xx/网络错误
|显示错误与重试入口
|假提示保存成功
|===

*旧请求覆盖*：每次选择记录请求序号与目标 ID，只有序号和目标都匹配才回填；切换账号后清理状态。

*重复保存*：保存期间禁用提交；成功后用服务器返回的集合与版本更新页面。

== 9. 并发、事务与一致性

=== 9.1 两个版本号

[cols="2,2,3",options="header"]
|===
|字段 |所在表 |管什么

|`role_version`
|`sys_user`
|用户的角色集合版本

|`permission_version`
|`sys_role`
|角色的授权集合版本
|===

两者独立递增：改用户角色动 `role_version`；改角色授权动 `permission_version`。

=== 9.2 乐观并发与行锁

* 读取时带回版本号，提交时带同一版本。
* 更新使用 `WHERE version = ?` 条件更新，影响行数为 0 即冲突。
* 冲突返回 409，附 `currentVersion`。
* 改造角色或用户前先 `SELECT ... FOR UPDATE` 锁定目标行，把并发写串行化。

=== 9.3 加锁顺序

用户角色替换需要锁多个角色行。实现先把「原有角色 + 新角色」合并，按角色 ID 数值升序排序，再逐个加锁。

原因：若事务 A 锁 {5,7}、事务 B 锁 {7,5}，两边各持一把互相等待会死锁；统一升序后加锁顺序一致，不会成环。

=== 9.4 隔离级别

* MySQL 默认 `REPEATABLE READ`。
* `SELECT ... FOR UPDATE` 是当前读加行锁；在 RR 下还会产生间隙锁。
* 因此更需要统一加锁顺序，避免范围锁交叉。
* 版本号冲突的 `currentVersion` 通过锁定当前读获取，避免快照返回过期值。

=== 9.5 事务边界

* `@Transactional` 只在 Service 层，Controller 不写事务注解。
* 整组替换、删除角色、重置密码等多步操作在同一事务内。
* 任一步异常全部回滚，不留半套授权。
* 删除角色后逐一对受影响用户递增 `role_version`。

=== 9.6 失败与回滚

* 保存中途失败：授权与版本保持原值。
* 并发抢输：409，不覆盖成功方结果。
* 删除确认与并发分配：先锁角色行，后执行的一方看到最新关系，未确认删除返回 409。
* 重复提交：版本已变，409 提示重新读取。

=== 9.7 已知限制

* 会话在单机内存，多实例部署需要会话共享。
* 未使用分布式锁；当前单实例部署足够。
* 未做缓存，权限每请求查库；这是用性能换一致性。

== 10. 安全设计

=== 10.1 认证与会话

* 登录成功轮换会话 ID，防会话固定。
* Cookie `HttpOnly`、`SameSite=Lax`；HTTPS 启用 `Secure`。
* 退出使旧会话失效。
* 账号停用、密码重置后，旧会话下一次请求即失效。

=== 10.2 密码

* 使用 PBKDF2，带算法前缀存储；兼容已有 BCrypt 哈希校验。
* PBKDF2 处理完整 8–128 字符，避免 BCrypt 72 字节截断。
* 不存明文，不返回哈希；响应只经 `Views` 构造。
* 初始密码来自部署配置，不写入仓库。

=== 10.3 授权

* 每个受保护接口逐请求检查：认证 → 权限码 → 数据范围 → 目标。
* 身份只从会话取；忽略前端传来的用户、角色、权限。
* 默认拒绝：没有明确授予、未知权限码、权限未加载一律拒绝。
* 查看范围不放大编辑范围。

=== 10.4 信息不泄漏

* 四种登录失败统一 401，不暴露账号是否存在。
* 范围外与不存在统一 403 `OUT_OF_SCOPE`，`details` 为空。
* 列表先裁剪范围再分页，避免 `total` 泄漏。
* 未知异常返回 500，不输出堆栈。

=== 10.5 输入与 SQL

* DTO 使用校验注解；失败统一 400 `VALIDATION`。
* Mapper 全部参数化 SQL，不拼接用户输入。
* 台账只允许修改电话、邮箱，其他字段 400 `FIELD_NOT_EDITABLE`。
* ID 长度与格式校验，避免超大数字或畸形 ID 进入 SQL。

=== 10.6 跨域与 CSRF

* 生产同源部署，不需要 CORS。
* 开发期前后端分离时由 Vite 代理或后端 CORS 配置处理。
* 会话 Cookie `SameSite=Lax` 降低 CSRF 风险；未实现 CSRF Token，属于已知简化。

=== 10.7 已知缺口

* 演示环境为 HTTP，未配置域名与 HTTPS。
* 未实现登录失败锁定（LOGIN-06，阶段三）。
* 未实现审计日志（阶段三）。
* 演示账号统一密码，仅用于合成数据。

== 12. 部署设计

=== 12.1 拓扑

Docker Compose 三服务：

* `db`：MySQL 8.4，内部网络，命名卷 `mysql_data`。
* `backend`：Spring Boot，内部网络，不发布端口。
* `web`：Nginx，发布 `HTTP_PORT`（演示为 8080）。

=== 12.2 镜像

* 后端多阶段构建：Maven + JDK 构建，JRE 运行，减小镜像。
* 前端：Node 构建，Nginx 托管静态文件。
* 依赖版本由 `pom.xml`、`package-lock.json` 锁定。

=== 12.3 配置

* `deploy/.env` 提供数据库密码、初始密码、端口、演示开关；权限 600，不提交。
* `.env.example` 只有占位符。
* 数据库与后端端口不发布公网；只开放 Web 端口。
* 演示数据 `RBAC_DEMO_ENABLED=true`，仅空库生成合成数据。

=== 12.4 健康检查

* MySQL：`mysqladmin ping` 或 `SELECT 1`。
* 后端：`GET /api/v1/health` 返回 `{"status":"UP"}`。
* Nginx：`/nginx-health`。
* Compose 使用 `depends_on: condition: service_healthy` 控制启动顺序。

=== 12.5 持久化

* MySQL 数据在命名卷；`compose down` 不删卷，`down -v` 才删。
* 重启验证：创建临时账号 → down → up → 确认账号仍在 → 清理。
* 会话在内存，重启后需要重新登录。

=== 12.6 Nginx 与同源

* 托管 Vue 静态文件、`/stage1/`、`/api-design/`。
* 代理 `/api/v1` 与 Swagger 到后端。
* 同源避免跨域 Cookie 问题。
* 数据库和后端端口留在内部网络。
