# 需求访谈记录（grill-me）

本记录是 [需求规格说明书](req-spec.md) 的来源：每条需求的结论与理由都可以在这里找到。

- 方法：按课程的 AI 辅助开发流程，需求分析阶段用 grill-me skill（[mattpocock/skills](https://github.com/mattpocock/skills)，它会转调同仓库的 `grilling` skill）做“AI 提问、成员 1 回答”的需求访谈。AI 把需求看成一棵决策树，每轮提出当前可以决定的问题并给出推荐答案，由成员 1 决定采纳或改写；事实（文件、数据、分支内容）由 AI 自己查证，不问人。
- 依据：本仓库的 [需求范围](scope.md)、[待确认问题](questions.md)、各成员的设计文档与分支，以及三份课程 Excel。
- 回答人：成员 1（替全组做需求分析）；第 5 轮根据群主在组内聊天中的意见复议。老师才能回答的问题见文末，状态仍为待老师确认。
- 日期：2026-10-15。共 6 轮 44 题（第 6 轮在收到员工信息表后补问）。

## 第 2 轮：RBAC0 的基本规则

成员 1 的回答：“仔细斟酌后按推荐来；需要问老师的提出来”。复查后推荐不变，只补充了细节（见 Q8、Q16）。

| 编号 | 问题 | 结论 |
| --- | --- | --- |
| Q7 | 谁能登录 | 所有启用的账号都能登录同一个系统，登录后看到按权限生成的门户菜单（占位页 + 员工台账）；管理后台菜单只对拥有 `rbac:*` 管理权限的人显示。这推翻成员 2 原型里“普通员工不能登录”的规则 |
| Q8 | 登录标识 | 工号或手机号 + 密码。手机号来自员工表，可以为空，不为空时唯一。会话用 Cookie 还是 Token 留给接口设计阶段（成员 6 草案为 HttpOnly Cookie） |
| Q9 | 超级管理员 | 清单的“系统管理员”就是超级管理员角色；系统只预置一个账号 `admin` 拥有它，界面上不能把这个角色授给别人 |
| Q10 | 部门管理员 | 保留成员 2 加的“部门管理员”，文档注明是平台自己的管理角色，不来自清单。范围见 Q18 |
| Q11 | 临时运维账号 | 找不到出处。除非老师或评分标准有要求，RBAC0 不做账号类别；先向成员 2 确认来源 |
| Q12 | 权限码格式 | `系统码:资源:动作`。18 个系统各取短码 (如 `hr`)；清单功能点用编号做资源段，如 `hr:f046:edit`，清单行顺序变化时编号不变；动作用 read / create / edit / approve / export / delete；管理后台用成员 3 的 `rbac:*` 码。需求只规定格式和“权限码稳定，不随显示名称变化” |
| Q13 | 清洗规则（老师问题 Q-07、Q-08） | H117、G310 中的英文 `view` 按“查看”处理；I340 空白按“不授予”处理；每条清洗记录原表位置 |
| Q14 | 单元格语义（老师问题 Q-09、Q-10） | “查看/编辑本人”两个操作都限本人；“全部”= 6 种操作全部授予，范围是全部；“无”= 不授予，不是显式拒绝；不带“本人”的操作范围是全部。**第 5 轮修订**: 部门经理、项目经理的管理类操作改为“本部门”，见 Q38 |
| Q15 | 多角色合并 | 取并集；同一权限码被多个角色授予时取最大范围（第 5 轮起顺序为 全部 > 本部门 > 本人）；范围只在同一权限码内合并 |
| Q16 | 初始角色（老师问题 Q-11、Q-12） | 部门表登记的经理按部门类型分配：项目经理部→项目经理，总公司和“公司领导”→公司领导，其余（含分公司经理）→部门经理；其他员工→普通员工；允许多角色；总公司与“公司领导”的负责人是同一人，按同一账号处理；负责人按用户 ID 关联 |
| Q17 | 授权变更生效时机 | 下一次请求即按新权限检查，不需重新登录；前端在授权操作成功后重新拉取权限 |

复查 Q14 时核对的事实：清单 1794 个权限格（359 × 5 − 1 个空白）中，带“本人”的只有“查看/编辑本人”（3 格）和“查看本人”（3 格）两种写法，没有“查看本人/编辑”这类混写，所以“整格按本人”不会误伤。“查看”也限本人的理由：清单另有“查看本人”写法，说明“本人”会修饰查看；若查看为全部，普通员工能看全公司员工的合同、薪酬档案，不合常理。

## 第 3 轮：RBAC0 的细节

成员 1 授权“按推荐”，以下结论为 AI 推荐并经复查，待成员 1 最终确认。

| 编号 | 问题 | 结论 | 理由 |
| --- | --- | --- | --- |
| Q18 | 部门管理员管到哪里 | 管理范围是本部门及全部下级部门。能做：查看、新增、编辑、启停范围内的用户，给范围内用户分配或撤销业务角色。不能：分配管理类角色（超级管理员、部门管理员）、修改角色授权、管理范围外的用户。部门管理员由超级管理员任命 | 分公司是有下级的节点，只管本部门的话，分公司的管理员没法管下属部门和项目部；禁止分配管理类角色，防止部门管理员自我扩权 |
| Q19 | 管理后台和清单第 18 个系统的关系 | 清单“系统管理后台”里我们实现的模块（用户管理、角色管理、权限配置、组织架构管理、登录日志、操作日志）的授权，映射成对应的 `rbac:*` 权限；系统 18 的其余功能点做占位页。映射表在接口设计阶段写入契约 | 这样清单的原意（公司领导对后台只读）仍然成立，也不会出现“目录里一套码、后台另一套码”两套东西 |
| Q20 | 账号与角色保护 | 不能停用、删除自己；不能修改自己的角色；唯一超级管理员账号不能被停用、删除或改角色；超级管理员角色的权限不能修改；内置角色（清单 5 个 + 部门管理员）不能删除，除超级管理员外可以修改授权。违反时拒绝并说明原因 | 沿用成员 2 原型的规则；防止误操作导致没人能管理系统，也防止自我扩权 |
| Q21 | 员工台账业务 | 列表按查看范围显示（只有本人范围的人只看到自己一行）；字段：工号、姓名、部门、岗位、电话、邮箱；编辑只能改电话和邮箱，且按编辑范围检查（第 5 轮起部门经理能看全部、只能改本部门员工）；新增、删除、审批、导出按钮按权限显示，点击为占位；改 URL 或 ID 访问范围外的记录被拒绝，且不返回该记录的任何内容 | 足够演示“仅本人”范围 (T-09)，又不重复用户管理的功能 |
| Q22 | 第一阶段管理后台做哪些 | 用户：列表（筛选、分页、按管理范围）、新增、编辑基本信息、启停、重置密码、删除、分配角色（整组替换 + 版本号）。部门：只读树。角色：列表、新增、编辑、启停。角色授权：在资源树上勾选操作和范围，整组替换 + 版本号。权限/资源目录：只读。个人：我的权限、修改密码。不做：部门和资源目录的增删改、授权矩阵页面 | 部门和资源目录都来自 Excel 导入，增删改不是 RBAC 的重点；授权矩阵用 SQL 演示即可 |
| Q23 | 密码与初始账号 | 密码用加盐的慢哈希存储。导入脚本只能用 Python 标准库，所以生成 Spring Security 能识别的 PBKDF2 哈希 (`{pbkdf2@SpringSecurity_v5_8}`)，最终算法与成员 4（他已用 BCrypt）统一（这一条是成员 1 整理数据库设计时定的）。导入账号的初始密码在导入时通过参数指定，不写进仓库；首次登录必须修改密码 | 仓库公开且最终部署到公网云服务器；需求初稿里的“SHA-256 加盐、阶段三再升级”不再需要 |
| Q24 | 员工表到位前 | 用部门表的负责人生成账号，另加 1 个演示普通员工（本地脚本已实现）；员工表到位后全量导入；生成的种子数据只在本地或服务器上生成，不提交到仓库 | 公开仓库不能放员工姓名和密码哈希 |

## 第 4 轮：RBAC1、RBAC2 与第三阶段

| 编号 | 问题 | 结论 | 理由 |
| --- | --- | --- | --- |
| Q25 | 层级结构（老师问题 Q-05） | 允许多个上级（DAG，一般层次）；senior 继承 junior 的权限；禁止自环和间接环 | 抽取公共角色后，一个角色往往要同时继承“全员基础”和“管理岗基础”两个公共角色，单父树表达不了 |

| Q27 | 停用角色与继承 | 停用的角色不贡献权限，经过它的继承路径也断开；有效权限页面标明每条权限是直接授予，还是继承自哪个角色 | 规则简单，演示时容易解释 |
| Q28 | 做哪些约束（老师问题 Q-13） | 必做：静态互斥 (SSD)、动态互斥 (DSD)、基数（角色人数上限、每人角色数上限）。先决条件约束不做，列为可选 | scope.md 写的是 SSD、DSD；验收矩阵 T-08 有人数上限；先决条件没有出现在组内任何资料里 |
| Q29 | 约束样例（老师问题 Q-13） | 清单角色之间没有天然的互斥关系，用自建的能力角色构造样例，如“付款经办”与“付款复核”做静态互斥，“申请提交”与“申请审批”做动态互斥（参照成员 3 的候选） | 不能声称样例来自清单 |
| Q30 | 约束与继承叠加 | 互斥沿继承传递：B、C 互斥且 A 继承 B，则 A、C 也互斥；修改继承关系导致违反约束的，同样拒绝 | 否则可以通过继承绕过互斥 (T-10) |
| Q31 | 什么时候校验约束 | SSD、基数在分配角色时校验，DSD 在激活角色时校验；新增约束时如果已有数据违反，拒绝保存并列出违反的用户；数据库层再用触发器兜底 SSD 和基数，绕过接口直接写库也会被拦下 | 库里永远不会出现违反约束的数据；两套后端共用同一个数据库兜底 |
| Q32 | 会话与激活角色 | 登录时默认激活全部已分配的角色；有动态互斥冲突时必须先选择；会话中可以切换激活的角色；鉴权只计算激活的角色 | 对应接口草案的 `POST /session/active-roles` |
| Q33 | 函数式模块（老师问题 Q-13） | 有效权限计算（继承展开、范围合并、约束检查）写成纯函数，放在面向对象后端里，有独立的单元测试 (T-13) | 这部分是“输入角色和授权、输出权限集合”的纯计算，最适合函数式 |

| Q35 | 第三阶段的附加内容 | 登录日志和授权变更日志（只能新增，不提供修改和删除）；连续 5 次登录失败锁定 15 分钟；数据库优化（索引和 EXPLAIN 报告）、数据字典、备份、云部署（成员 1 负责） | 日志对应清单的登录日志、操作日志两个功能点；审计日志能删就失去追责意义 |

## 第 6 轮：员工信息表到位后补问

员工信息表共 10,000 名员工，列为姓名、用户名（`SG000001` ~ `SG010000`）、分公司、部门、岗位、电话号码，没有性别和邮箱。核对结果：“分公司 + 部门”全部能对上部门表的 111 个组织单元；用户名、手机号没有重复和空值；有 1,596 个姓名重复出现（涉及 3,737 人）；部门表的负责人有 110 人能按“同名 + 同部门”找到，总公司负责人登记在“公司领导”部门。按 Q16 的规则，只有这 110 人有领导或经理角色，于是“公司领导”部门的 9 位领导和全部副职都成了普通员工，需要补问。成员 1 的回答：Q41–Q44 全部采纳推荐。
