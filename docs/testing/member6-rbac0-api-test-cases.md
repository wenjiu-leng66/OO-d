## 1. 测试目标

第一阶段主要确认以下行为：

- 没有登录时，受保护接口不能访问。
- 已经登录但没有所需权限时，后端必须拒绝，不能只依赖前端隐藏按钮。
- 有权限且目标数据在管理范围内时，请求可以成功。
- 修改 URL、用户 ID、角色 ID 或请求体，不能绕过对象范围与可授出范围。
- 用户角色和角色权限采用完整集合替换，撤销必须真实生效。
- 版本冲突和非法集合不能造成部分写入。
- 错误状态与 OpenAPI 一致，并返回可定位但不泄露秘密的错误信息。

RBAC1 的角色继承以及后续 SSD、DSD、人数上限等约束不属于本轮执行范围。

## 3. RBAC0 权限拦截用例

### API-001：未登录访问受保护查询

- 对应验收项：T-01。
- 前置条件：客户端没有有效会话。
- 操作：请求 GET /api/v1/users。
- 预期：返回 401；错误码为 UNAUTHENTICATED 或团队确认的等价码；不返回用户列表。
- 当前状态：待后端联调。

### API-002：未登录直接修改用户角色

- 对应验收项：T-01。
- 前置条件：客户端没有有效会话，已知一个合成用户 ID。
- 操作：请求 PUT /api/v1/users/{userId}/roles，并提交角色集合。
- 预期：返回 401；数据库中的用户角色关系完全不变。
- 当前状态：待后端联调。

### API-003：普通员工访问用户列表

- 对应验收项：T-02。
- 前置条件：普通员工已登录，但没有 rbac:user:read。
- 操作：请求 GET /api/v1/users。
- 预期：返回 403；不能以 200 加空数组伪装成无数据。
- 当前状态：待后端联调。

### API-004：只有读取权限的账号修改角色授权

- 对应验收项：T-02。
- 前置条件：角色查看员具有 rbac:role:read 和 rbac:permission:read，但没有 rbac:role:grant。
- 操作：先成功读取角色权限，再请求 PUT /api/v1/roles/{roleId}/permissions。
- 预期：读取返回 200；修改返回 403；角色权限集合和版本不变。
- 当前状态：待后端联调。

### API-005：管理员正常读取当前有效权限

- 对应验收项：T-02。
- 前置条件：超级管理员 A 已登录。
- 操作：请求 GET /api/v1/me/permissions。
- 预期：返回 200；userId 与当前会话一致；角色与权限数组无重复；不接受查询他人的 userId 参数。
- 当前状态：待后端联调。

### API-006：有权限时正常查询用户

- 对应验收项：T-02。
- 前置条件：超级管理员 A 具有 rbac:user:read。
- 操作：请求 GET /api/v1/users?page=1&pageSize=20。
- 预期：返回 200；包含 items、page、pageSize、total；结果只包含允许范围内的用户。
- 当前状态：待后端联调。

### API-007：部门管理员读取其他部门用户

- 对应验收项：T-09。
- 前置条件：部门管理员已登录；U2 属于其他部门。
- 操作：把正常用户详情 URL 中的用户 ID 改成 U2，调用 GET /api/v1/users/{U2}。
- 预期：返回 403，或按团队最终防枚举规则返回 404；不能返回 U2 的姓名、电话、角色或其他资料。
- 当前状态：数据范围规则待确认，随后联调。

### API-008：部门管理员修改其他部门用户角色

- 对应验收项：T-09。
- 前置条件：部门管理员具有角色分配操作码，但 U2 不在其管理范围内。
- 操作：请求 PUT /api/v1/users/{U2}/roles。
- 预期：返回 403 或确认后的防枚举结果；U2 的角色、权限和版本均不变化。
- 当前状态：数据范围规则待确认，随后联调。

### API-009：分配角色后获得权限

- 对应验收项：T-03。
- 前置条件：U1 初始没有代表性权限 P；管理员读取到当前角色集合版本。
- 操作：将包含权限 P 的角色加入完整 roleIds 集合并 PUT 保存，然后重新查询 U1 的角色和有效权限。
- 预期：保存返回 200，版本递增；U1 获得 P。对 U1 已有会话何时生效，按最终契约核对并记录。
- 当前状态：待后端联调。

### API-010：撤销角色后权限消失

- 对应验收项：T-03。
- 前置条件：U1 的权限 P 只来自待撤销角色。
- 操作：提交不包含该角色的完整 roleIds 集合，再查询有效权限并调用受 P 保护的接口。
- 预期：角色被撤销；P 不再出现；受保护接口返回 403。失败时不能保留旧授权缓存继续放行。
- 当前状态：待后端联调。

### API-011：角色权限完整集合替换

- 对应验收项：T-03。
- 前置条件：角色 R 直接拥有权限 P1、P2，已读取版本 V。
- 操作：PUT 只包含 P2、P3 的 permissionCodes 和版本 V。
- 预期：成功后集合恰好为 P2、P3；P1 被撤销；版本递增；不能变成 P1、P2、P3 的追加结果。
- 当前状态：待后端联调。

### API-012：未知角色或权限不得部分写入

- 对应验收项：T-03。
- 前置条件：准备一个合法 ID 和一个不存在的角色或权限码。
- 操作：在同一个 PUT 集合中同时提交合法项和未知项。
- 预期：返回 400；合法项也不能写入；原集合与版本保持不变。
- 当前状态：待后端联调。

### API-013：重复集合元素被拒绝

- 对应验收项：T-03。
- 前置条件：已读取当前版本。
- 操作：提交包含重复 roleIds 或 permissionCodes 的 PUT 请求。
- 预期：返回 400；不自动猜测或静默保存；原集合与版本保持不变。
- 当前状态：待后端联调。

### API-014：并发版本冲突

- 对应验收项：T-03。
- 前置条件：管理员 A、B 都读取到版本 V；A 先成功保存并得到 V+1。
- 操作：B 仍使用 V 提交不同集合。
- 预期：B 返回 409 VERSION_CONFLICT；A 的结果不被覆盖；响应可返回当前版本但不能泄露不可见数据。
- 当前状态：待后端联调。

### API-015：停用账号后旧会话不能继续操作

- 对应验收项：T-01、T-02。
- 前置条件：U1 已登录并持有有效会话，管理员随后停用 U1。
- 操作：U1 使用原会话再次请求受保护接口。
- 预期：后端拒绝请求；具体返回 401 还是 403 由团队统一，但必须与 OpenAPI 和前端处理保持一致。
- 当前状态：状态码待确认，随后联调。

### API-016：请求体伪造权限不能越权

- 对应验收项：T-02、T-09。
- 前置条件：普通员工已登录，没有管理权限。
- 操作：在请求体或自定义请求头中加入 role=admin、permissionCodes 或 userId 等伪造字段，再调用管理接口。
- 预期：后端忽略不可信授权声明并返回 403；不能依据客户端自报角色放行。
- 当前状态：待后端联调。

## 5. 联调前必须确认的问题

1. 登录最终使用 HttpOnly Cookie 还是 Bearer Token；会话失效、退出和 CSRF 如何处理。
2. 用户角色分配统一使用 rbac:user:assign-role，还是暂时复用 rbac:user:update。当前 OpenAPI 采用前者，现有 Mock 使用后者。
3. 工作台只要求登录，还是要求 rbac:user:read。
4. 角色或权限变化对已有会话立即生效、重新查询生效，还是重新登录生效。
5. 越权目标统一返回 403 还是为了防对象枚举返回 404。
6. all、department、self 范围的确切含义和合并规则。
7. 是否禁止修改自己、唯一超级管理员以及内置管理员角色，冲突使用什么错误码。

确认结论后，应同时更新 OpenAPI、前端适配、后端实现、本测试文档和验收矩阵。
